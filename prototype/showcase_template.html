FORGE Report Mining

Ten public drilling documents from three geothermal wells, turned into a queryable database by two small open models running on one 8 GB laptop GPU. Every value below was extracted automatically from PDF text or figures. Nothing was typed by hand.

How it works

Pipeline

  1. Read the PDFPyMuPDF rebuilds each page as monospace text so table values stay under their column headers. Compilations are split into single reports.
  2. Extract per tableQwen3-8B fills one schema per table (header, time log, casing, mud, bits, BHA, surveys) as validated JSON.
  3. Check and classifyPhysically impossible values are nulled and flagged. A second pass labels problem events row by row. NPT comes from the operator's Non-Prod marks where a document has them, otherwise from the same pass.
  4. Read the figuresFigures are cropped with their captions. Qwen2.5-VL-7B describes each one, then structures curves and numbers. The Pason chart is parsed directly from the PDF, with no model.
  5. Store and askEverything lands in SQLite. A tool-using agent answers questions across all reports with SQL.

End-of-Well Report digest

Well 56-32's End-of-Well Report read in chunks. Each chunk gets one call for well facts and tables and one for problems and lessons; the results are merged. Well facts, problems and lessons are reliable. The casing and bit tables are not yet: rows repeat across chunks and some hole sizes land in the casing OD column.

Figures and plots

What the vision model read

Each figure is detected on the page (logos and ruled tables are skipped), cropped with its caption, and passed to the vision model with any machine-readable text inside it. Numbers the model reads off curves and logs are often wrong, so they are not shown here. The Pason chart's values come from direct PDF parsing instead.

What tuning taught us

Design choiceObserved on test reports
One call for the whole daily-report schemaHeader and time log filled; casing, mud, bits and BHA came back empty.
Plain extracted textColumn values drift: grade read as "FULL", chlorides off by orders of magnitude.
Monospace layout text + one call per tableSurveys, casing shoes, mud check and header correct; BHA 11 of 12 components fully correct on a WellEz report.
Reasoning mode on (Qwen3 "thinking")5 to 15 times slower per table with no accuracy gain.
Dedicated NPT and event classifier with examplesRemoved false NPT on routine trips and false "events" for safety meetings and rig-up.
Plausibility rangesCatch decoding errors such as chlorides = 7.2e15 mg/l and pump rate read as bit RPM.
Figure schema with description firstStructured lists went from empty to complete: all 9 BHA values and 8 MSE tracks with units.
Concrete numbers as examples in the figure promptThe model copied the example values into 14 of 62 figures (23%) where it could read no numbers.
"Leave empty if nothing is legible"Leakage gone, but 43 of 62 figures then returned no values at all, including BHA diagrams it had read correctly before.
Transcribe first, then describe, then structureBHA diagrams read in full again with no leaked values. Dense multi-track charts are still the limit: numbers are read but given the wrong meaning (depth read as ROP, scale limits read as values).
Domain glossary in the promptsWithout it, both models expanded MSE as "mean square error" instead of mechanical specific energy.
Agent grounded with real category values and a retry ruleBefore: the agent invented filter values ("losses", "failures") and answered "no BHA data" from one empty query, with 287 BHA rows in the database.
Figure category list without pressure charts or equipment drawingsAbout 67% correct against captions; most errors were cement charts and BOPE drawings forced into the nearest class. Two classes added.
One mixed schema for long reportsEnd-of-Well Report: events and lessons found, but no well facts, casing or bits. Split into a facts call and a narrative call.
Generation limitsDense mud-log pages triggered a runaway list (7,000+ tokens). An output cap and repeat penalty fixed it. A 16k context pushes the 8B model partly onto the CPU on an 8 GB GPU.

Prompts were tuned on reports D01, D02 and D05, so these count as the development set. Prompt examples were rewritten so none come from the evaluated reports. Known weak spots: dense mud and bit-parameter tables with multi-row headers still show column shifts; problem-event detection finds the real incidents but also flags some planned work (roughly 60 to 65% precision on a spot check); tables in the long report come back fragmented across chunks. A field-level accuracy study against hand-labelled reports is the next step.

Data: Utah FORGE wells 16A(78)-32, 56-32 and 78B-32, US DOE Geothermal Data Repository, CC BY 4.0.
Models: qwen3:8b (text) and qwen2.5vl:7b (vision) via Ollama, run locally. Prototype for a follow-up to SPE-228955-MS.
